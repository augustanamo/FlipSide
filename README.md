# FlipSide（MagFoldCast）

折叠屏通用小工具：**把选中的图片/动图/视频铺到外屏上，内屏留着当控制台。**
（图片、GIF、视频可以混选；GIF 在外屏上是真的在动，不是一张首帧。）

和 MagFold（读杂志）、MagFoldMusic（氛围音乐）共用同一套「双屏幕模式」实现，
但这个是纯工具 —— 不绑定任何内容形态，选什么就展什么。

```
应用名     FlipSide
包名       com.magfold.cast
版本       0.5.1
minSdk     29    （ImageDecoder / ContentResolver.loadThumbnail 从 29 起可用）
compileSdk 36
真机       Galaxy Z Fold 8（SM-F971B），已装过前两个工程
```

> 应用名从 0.3.0 起叫 **FlipSide**。**包名与工程目录仍是 `com.magfold.cast` / `MagFoldCast`** ——
> 改 `applicationId` 会让系统把它当成另一个应用（覆盖安装变成并排两个），
> 与「改个显示名」不是同一件事，所以没动。

## 它不是预览器，是展窗

这句话决定了后面所有设计。区别在这三处：

| | 预览器 | 展窗 |
| --- | --- | --- |
| 外屏内容 | 画面 + 按钮 + 标题 + 页码 | **只有画面，一个控件都没有** |
| 切到别的 App | 停播 | **继续展**（进程被前台服务保住） |
| 开机 | 手动打开 | **自己回到展出状态** |

所以外屏不承担任何操作职责 —— 它可能挂在墙上、锁在柜里、立在店里，没人站在它面前按按钮。
所有操作都在内屏控制台里（`ui/ConsoleScreen.kt`）。

## 四种形态

| 场景 | 内屏 | 外屏 |
| --- | --- | --- |
| 展开 + 支持双屏 + 投屏开 | 控制台 | **纯画面** |
| 展开 + 分栏预览开 | **一侧纯看（按外屏长宽比）+ 一侧控制台** | 同左栏（若真投着则同步） |
| 折起 | —— | Activity 被系统挪到外屏，本体直接铺满 |
| 展开 + 本机不支持双屏 + 投屏开 | 全屏画面（「铺满内屏」） | —— |

前两种走 Android 14 的双屏幕模式（`OPERATION_PRESENT_ON_AREA`）。
国产折叠屏基本没有部署 window area 扩展，所以最后一种在那些机器上是常态 ——
「把手机立起来当展窗」同样是正常用法。

**判据是「能力」而不是「此刻在不在投」**，这一条是被 bug 教会的：`presentContentOnWindowArea`
是异步的，从发起到 `onSessionStarted` 之间有一段空窗，那段时间 `presenting` 还是 false。
早先按后者判定，于是点「投到外屏」会先进最后一种形态 —— 素材被放大铺满内屏，
等会话起来再切回控制台，「点投屏先放大一下」就是这么来的。现在：

- `CoverStatus.detected`：探测**有结论**之前，不认为「不支持」；
- `CoverStatus.requesting`：请求发出、会话未起时状态写成「正在投放到外屏…」，界面留在控制台；
- 两道超时兜底：探测 2.5s 无结论按不支持落定，请求 6s 等不到回调退回控制台。

## 主界面只放三件事

这台设备多半立在桌上，人是**偶尔过来调一下**，不是长期盯着一张设置表。
所以主界面只剩：素材、翻片、开关状态；其余全部收进底部的设置面板（`ui/SettingsPanel.kt`）。

```
FLIPSIDE                                      ＋ 素材   设置
外屏待命
8 件素材 · 当前 3/8 · 轮播 10 秒
─────────────────────────────────────────────────────────
              [ 素材网格 ]
─────────────────────────────────────────────────────────
        [ 上一张 │ 投到外屏 │ 预览外屏 │ 下一张 ]
```

设置面板里是：轮播间隔、**视频（播完再切 / 按间隔）**、画面（填满/适应）、声音、
**播放/暂停**、预览位置（左/右）、后台保持、**外屏常亮**、开机自启、清空素材（两段确认），
底部再写一行外屏实测尺寸与状态。
（播放/暂停只对视频有效：暂停会把画面定格在当前这一帧。）

两个细节值得单独说：

- **面板挂在控制台内部**，所以分栏预览时它只盖住控制台那一栏，预览栏照旧可见 ——
  改设置时立刻能看到效果，这正是预览存在的意义。
- **控制条的激活段用字色深浅表达**（不做勾选框、不加背景）：一整条里出现两种深浅，
  读起来就是「这两段是开关，另外两段是动作」。投屏与预览可以同时点亮。

## 轮播

间隔可选 **关 / 5 秒 / 10 秒 / 30 秒 / 1 分钟**，默认关 —— 展窗该由人决定放哪一张，
自动换片是「要才开」的能力。四条约定：

1. **计时以「当前这件何时上屏」为准**，所以手动换片会重新计时，不会出现刚翻过去半秒就被换走。
2. 只在**展出或预览中**、**没被暂停**、且素材多于一件时推进；控制台开着但没展出时它不动。
3. **视频默认「播完再切」**（设置里可改）。轮播间隔**对视频不生效**：它一直放到尾，
   由 `STATE_ENDED` 触发换片。理由是 30 秒的间隔把 2 分钟的视频从中间切走，看着像坏了。
   唯一例外是解不出来/播不动的视频，那种等一个宽限期就跳过，不让整个轮播卡死。
4. 为此，轮播开着且素材多于一件时必须把播放器从 `REPEAT_MODE_ONE` 改成 `REPEAT_MODE_OFF` ——
   单曲循环的播放器永远走不到 `STATE_ENDED`，这也就是「轮播对视频不生效」的成因。

## 动图（GIF / 动态 WebP）

**支持，而且是真在动。** 实现上有一处必须绕开的坑：Compose 的 `Image` 只吃 Bitmap，
而 Bitmap 是「某一帧」—— 拿它画 GIF 等于把动图当静态图。要让帧动起来只能交给平台：

```
ImageDecoder.decodeDrawable() ──▶ AnimatedImageDrawable（自己按帧延迟推进）
                                      │
                                      └─▶ AndroidView 托一个 ImageView 装它
```

三个细节（都在 android-36 的 jar 上核过 API）：

- **`decodeDrawable` 放 IO 线程，`start()` 必须放主线程**。AnimatedImageDrawable 的帧回调
  挂在当前线程的 Looper 上，从 IO 线程 `start()` 会挂不上 —— 画面不动，而且**不报错**。
- **`repeatCount` 要在 `start()` 之前设成无限循环**。原图只播一遍的那种 GIF，
  在橱窗里等于一张不动的图。
- **一个 AnimatedImageDrawable 只能被一个 View 持有**，所以刻意不进 `LruCache`：
  分栏预览和真外屏会同时各画一份，共享实例会让其中一边被抢走。
  代价是每次组合重新解一次，换来两处都能正常动。

判定只看 MIME / 扩展名（`image/gif`、`image/webp`、`.gif`/`.webp`），不预先解一遍头 ——
网格里几十件素材逐件解头太贵。静态 WebP 会被一并标成「动图」，但它的画法（ImageView +
Drawable）对静态图同样正确，所以无所谓。网格里动图带一个 `GIF` 字标，跟视频那个 ▶ 区分开
（两者都会动，但动图不走播放器、没有时长、外屏上是一直播下去的）。

## 分栏预览：一侧纯看，一侧继续设置

点「预览外屏」，内屏按**外屏真实长宽比**切出一栏：栏内是**和外屏完全相同的那一个 composable**
（`CastStage`，一个按钮都没有），另一栏仍是控制台。两个附带好处：

- 一眼看出这张图在外屏上会被裁掉多少 —— 这正是「填满 / 适应」要判断的事；
- 预览栏里左右滑动就能换片（真实外屏那一份依然一个手势都没有）。

长宽比优先取 **window area 报的 `WindowAreaInfo.getMetrics().bounds`**（外屏的像素尺寸），
拿不到才用兜底常数，并在栏底照实写出「外屏 1080 × 2520」或「外屏尺寸未知」。
侧别（左/右）是设置项，默认左：外屏装在展开机身的哪一侧取决于厂商的堆叠方式，
装反了在设置里一点就换边。

**视频在预览栏里可能只显示首帧**，这不算故障：视频同时只能挂在一块屏上（`ExoPlayer` 的硬约束），
真投着外屏时播放器归外屏，预览栏拿不到播放器，只能显示首帧 —— 所以栏底会照实写
「视频正在外屏播放 · 这里是首帧」，免得一帧静止画面看起来像「预览坏了」。
没投外屏时预览栏拿得到播放器，视频就是正常播放的。

## 后台保活与开机自启

### 为什么必须靠保活

`presentContentOnWindowArea` **只接受 Activity**（window 1.5.1 里没有 SurfacePackage
那个重载，`javap` 确认过），所以外屏画面注定挂在 Activity 上。
那么「应用在后台不影响显示」就等于「别让系统把进程收走、别把 Activity 销毁」——
这正是 `serve/CastService` 存在的唯一理由：**它自己不画任何东西，只保证进程活着。**

早期版本用 Activity 的 `onStart/onStop` 当播放闸门（切出去就停播），那是把它当预览器的错，
已经删掉了。现在的闸门是**投屏态或预览态**：只有「收起外屏 / 退出预览」会停，退到后台不会。

保活服务只在「正在展出 + 后台保持」同时成立时运行。收起外屏还挂个常驻通知就是骚扰。

### 外屏常亮（0.5.0 加）

展窗自己会熄屏等于没展出，所以展出期间得攥住那盏屏。这里有两个坑：

- **不能用 `FLAG_KEEP_SCREEN_ON`。** 那个 flag 是**窗口级**的：只在窗口可见时参与系统的
  熄灭超时计算。而这个工具的正常工作状态恰恰是「应用不可见、外屏还在放」——
  窗口一不可见，flag 就等于没写，「锁屏走开也一直亮」它做不到。
- **只能靠 `PowerManager` 屏幕锁，且必须由保活服务持有。** WakeLock 是**进程级**的，
  与窗口可见性无关，正好对上这个诉求；但它要求进程活着，而应用不可见时唯一确定活着的
  就是这个前台服务。所以常亮天然是「后台保持」的下游 —— 三个条件
  `展出 && 后台保持 && 常亮` 缺一不可（`CastService.syncWake`）。

界面**不持锁**：改开关只是重投一次服务，服务自己读落盘的开关值去对齐。这样
「系统重启的服务」「开机自启拉起的服务」「界面刚改完开关的服务」走的是同一条对齐路径，
不会出现「界面开着常亮、服务那边却不知道」。实现在 `serve/ScreenWake.kt`。

三个刻意的选择：

1. 级别用 `SCREEN_BRIGHT` 而不是 `SCREEN_DIM` —— 视觉展示被系统调暗到几乎看不见等于坏了，
   该省电的地方在「什么时候持有」，不在亮度；
2. `setReferenceCounted(false)` —— 我们要的只是「亮 / 不亮」一个布尔状态。开着计数的话，
   界面每重组一次 acquire 一次、计数越堆越高，最后 release 一次根本放不掉，屏幕就永远亮着；
3. **不加** `ACQUIRE_CAUSES_WAKEUP` —— 屏幕本来就灭着时不必强行点亮，那是「人不在」的
   场景；等人拿起手机屏幕自然亮起，再由这把锁留住。

「常亮开着、后台保持关着」是无解组合（没人攥着进程，锁留不住）。所以设置面板会把它画成
暖棕色待处理状态，hint 本身就是那个补开关的入口，不让它变成一个静默失效的开关。

> 顺带说清 `WAKE_LOCK` 这条权限：它**在 0.5.0 之前就已经出现在打包结果里**了，
> 但不是我们申请的 —— 是 `androidx.media3:media3-exoplayer` 顺手带进来的
> （它支持 `setWakeMode`，那是 CPU 级别的锁）。我们从没启用过那个开关，
> 所以此前**并没有任何唤醒行为**。0.5.0 起是真要用它，改成了在清单里显式声明。

### 前台服务类型为什么是 specialUse

不是 `mediaPlayback`，有两个硬理由：

1. 它只对「正在播视频」成立，而展出图片时同样需要进程活着，按 `mediaPlayback` 报类型属于滥用；
2. **Android 15 起 `BOOT_COMPLETED` 被明确禁止拉起 `mediaPlayback`**（禁止名单：
   `dataSync / camera / mediaPlayback / phoneCall / mediaProjection / microphone`），
   而 `specialUse` 在允许名单内。这个工具迟早要在开机链条上用到它。

### 开机自启链条，以及它唯一的前提

```
BOOT_COMPLETED ──▶ BootReceiver ──▶ 拉起 MainActivity ──▶ 界面可见后自己起保活服务
                                    ↑
                        这一步被 BAL 限制挡住，需要系统「显示在其他应用上层」权限
```

关键对比（这两条一起记才不容易搞错）：

- `BOOT_COMPLETED` **可以**拉起前台服务（但类型受限，见上）；
- `BOOT_COMPLETED` **不能**拉起 Activity。

Android 10 起后台应用不能直接 `startActivity`，官方豁免清单里有一条是
**应用已获得 `SYSTEM_ALERT_WINDOW` 权限** —— 也就是设置里那句「显示在其他应用上层」。

**这个权限一共只被两条路径用到**，都收在 `AutoStart.launchConsole` 里：

| 路径 | 触发者 | 没授权时的后果 |
| --- | --- | --- |
| 开机自启 | `BootReceiver` | 开机不会自动展出 |
| 划掉任务自动拉回 | `CastService.onTaskRemoved` | 划掉最近任务后外屏黑掉，而且没人把它拉回来 |

所以它**不是**「只影响开机自启」：展出本身、以及后台保持里的外屏常显，全都正常
（那些只靠前台服务，一条权限都不要）；被拦下的只有上面这两条「从后台把界面拉起来」的路径。
两条都在控制台里画成暖棕色待处理状态、各给一行可点的授权入口，
不让它们变成静默失效的开关；没授权时 `AutoStart` 只记日志，不做任何假装成功的动作。

开机自启还有第二个条件：**上次退出时正在展出**。否则开机弹一个空控制台很唐突。

### 划掉最近任务会自己回来

`CastService.onTaskRemoved` 在「正在展出 + 后台保持」时会把界面拉回来重建展出。
这是刻意行为：挂在墙上的展窗不该因为顺手清了最近任务就黑掉。
**它跟开机自启共用同一个前提** —— 拉界面这一步同样要「显示在其他应用上层」，
所以「后台保持」开着而没授权时，那条 hint 也会变成可点的授权入口。

因此必须留一个不会被拉回来的停止方式 —— 通知栏的**「停止展出」**就是它
（会同时关掉投屏态并落盘，下次开机不会再自己回来）。不想要「划掉就回来」
就把设置里的「后台保持」关掉。

## 「一进后台外屏就黑」：到底有几种成因

这个现象被报过两次，**不是一个 bug，是一串**。0.3.0 只修掉了第一环，0.4.0 把剩下的补齐。

### 第一环：能力探测被取消，被当成了「探测失败」（0.3.0 修）

```text
应用进后台
  └─ Activity 落到 STARTED 之下
       └─ 探测循环外层包着 repeatOnLifecycle(STARTED) → 协程被取消
            └─ runCatching 把 CancellationException 当普通异常吞掉
                 └─ 能力被改写成 UNSUPPORTED 并对外发布
                      └─ 界面判定「本机不支持双屏」→ 把内屏顶成全屏舞台
                           └─ 内屏挂上同一个播放器 → 抢走外屏那块 Surface
                                └─ 外屏当场变黑
```

修法：探测循环不再绑在 `STARTED` 上、`CancellationException` 原样抛出、播放器归属改按会话判定。

### 第二环：外屏容器一 detach，组合就被销毁（0.4.0 修）

外屏容器会被系统**反复 detach / re-attach**（切后台、姿态变化、会话重建），
而两个默认行为叠在一起，让这个 View **一旦 detach 就永久作废**：

1. `AbstractComposeView` 的默认组合策略是 **`DisposeOnDetachedFromWindowOrReleasedFromPool`**
   （在 compose-ui 1.12.1 的字节码上核过：`ViewCompositionStrategy.Companion.getDefault()`
   返回的就是它）。也就是说 **View 一 detach，组合当场销毁、内容清空**，
   再 attach 回来只是一块空 View；
2. 早先的 `CoverComposeView` 还在 `onDetachedFromWindow` 里把生命周期打成 `DESTROYED`，
   而 `onAttachedToWindow` 又「不敢」把 DESTROYED 拉回 RESUMED（防重复 attach），
   于是它**永远回不来**。

修法：组合策略显式改成 `DisposeOnLifecycleDestroyed(this)`（只有我们主动销毁才销毁），
detach 只退到 `CREATED`（组合还在、帧时钟暂停），re-attach 回 `RESUMED` 就继续画。
detach 从此是一次暂停，不是一次死亡。真要销毁时由桥调 `disposeNow()`。

### 第三环：界面只信「此刻的能力值」，一转后台就翻脸（0.4.0 修）

内屏判自己该不该顶成舞台，靠的是「能力是否可用」。而应用不可见时，这个值可能一时读不出
`AVAILABLE`（会话也可能正被系统收走）—— 界面于是认为「本机不支持双屏」，去抢播放器。

修法：`CoverStatus.engaged` —— **本次展出周期里成功投上过外屏就记住**，
只要记着，内屏就绝不抢舞台（`selfStage` 与 `coverOwnsPlayer` 都看它）。
投上过就是投上过，机器支持这件事不会因为应用不可见而改变。收起外屏时清零。

### 第四环：自愈的窗口太短、且回来时没人复查（0.4.0 修）

- **重开外屏的退避**：早先是「最多 3 次、每次隔 800ms」= 只覆盖 2.4 秒，
  而会话被收走往往就发生在应用不可见的那几秒里 —— 等于没试。
  现在是指数退避（400ms→15s 封顶）共 8 次，**约 50 秒的窗口**。
- **回前台复查**：`MainActivity.onResume` → `CoverDisplay.refresh()`。外屏画面挂在
  Activity 上，应用不可见时系统可能把会话或容器收走，而那时我们既看不到也补不回来 ——
  回到前台是唯一确定的补救时机。会话没了就重开，内容可疑就重塞一份。
  这里只在**内容可疑**（容器被藏过 / 我们的 View 被 detach 过）时才重塞，
  否则从相册选完素材回来也会无谓地闪一下。
- **容器被藏起来时补一次内容**（3 次/分钟封顶），并记日志。

### 还有一种，是厂商那边的

如果日志显示容器被系统收起（`容器可见性 -> false`）而补内容也补不回来，
那就是**厂商实现在宿主 Activity 不可见时主动收起了展示容器** ——
外屏那幅画面是系统带着的，应用侧阻止不了，只能等回前台立刻补回来。

这一带的日志入口：

```bash
adb logcat -c && adb logcat | grep -E "WindowAreaBridge|CoverComposeView|AppRoot|ShowState|CastService"
```

最有用的是这五行：`外屏容器可见性 -> true/false`、`外屏状态 A -> B (可用 x->y 会话 x->y 曾投上 x->y)`、
`会话已结束但内容还在，第 N 次尝试重开外屏（等 Nms）`、`形态 casting=… 本体当舞台=… 播放器归外屏=…`、
`播放失败：<uri>`。**形态那一行**能一眼分清是「判成不支持了」还是「外屏容器被收走了」。

## 权限清单

只多了一个需要用户手动去系统设置里授予的权限，而且它跟展示能力本身无关：

| 权限 | 用途 |
| --- | --- |
| `SYSTEM_ALERT_WINDOW` | 从后台拉起界面（开机自启、划掉任务拉回）的唯一豁免条件。**与展示能力无关** |
| `RECEIVE_BOOT_COMPLETED` | 开机广播 |
| `FOREGROUND_SERVICE` + `FOREGROUND_SERVICE_SPECIAL_USE` | 保活服务 |
| `WAKE_LOCK` | 外屏常亮（`SCREEN_BRIGHT_WAKE_LOCK`）。普通权限，装完即有 |
| `POST_NOTIFICATIONS` | 保活服务的通知。拒绝也不影响展出，只是通知栏看不到、「停止展出」那个出口也没了 |

**存储权限一条都没有**：选素材走系统照片选择器（`PickMultipleVisualMedia`），
授予的是「用户勾中的这几个文件」的读权限，不是整个相册。

## 界面质感的来源

参考图是一张「全屏影像 + 极简编辑排版」的样张，从中取了三样东西：

1. **内屏纸面色 `#EFEFF1`** —— 直接量的参考图里画面之外那层浅灰白。墨字、暖棕 `#7A5A42` 做唯一强调色。
2. **多段式控制条** —— 参考图里 `SHOW ALL / SHOP / IDENTITY` 那一排。关键是它
   **一整块圆角矩形内部等分若干段、段间只有 1px 竖线**，而不是几个独立小按钮；
   这个区别就是「版式感」和「设置项」的区别。见 `ui/GlassRow.kt`。
   *（这排按钮现在只出现在内屏控制台，外屏那份已按「纯展示」原则撤掉。）*
3. **宽字距大写小字** —— 所有标签都是 `letterSpacing 0.12~0.34em` 的大写小字号。

**但「玻璃」这件事在纸面上不成立，已退回细线。** 参考图那层半透明白之所以好看，
前提是它压在一张画面上：实测参考图条内亮度 227~229、背后是亮度 83 的画面，有东西可透才叫玻璃。
搬到纯纸面后，90% 白的填充实测出来是 253，而纸面是 239 —— 只差 5.5%，读起来是一块
**不透明的白板**；再叠 10dp 投影（实测条下最暗 187，比纸面暗 20%），就成了
「白卡贴纸 + 深色描边」，像背后压了第二张白纸。

所以纸面上的控件一律只留 1px `12%` 墨的细线，跟页眉分隔线、段间竖线同一种语言。
设置面板的上缘用一条 `30%` 墨的稍重线交代「这是一张推上来的纸」，也不靠投影。

## 几个关键决策

**一个播放器，同一时刻只挂一块屏。**
`ExoPlayer` 不支持两个视频视图同时接同一个实例。工程靠两侧保证：
UI 上按「谁拥有这块屏」互斥 —— 折起时本体就是外屏；本机具备投放能力时那块屏交给会话；
分栏预览栏只有在**没人替它拿播放器**时才挂（`attachPlayer = !coverOwnsPlayer`）。
再加 `VideoStage(enabled=)` 兜住折叠那一瞬间的重叠。

**「铺满内屏」与「分栏预览」在不支持双屏的机器上互斥。**
两者是同一个诉求的两种画法（都只是想在内屏看到画面），同时开着会变成两个开关都亮、
却只有一边有画面。点哪个就把另一个让掉；能真投外屏时不受此限（那时两者可以并存，
预览栏顺便当「外屏在显示什么」的回看）。

**视频出画前不黑屏：透明 shutter + 换片时保留上一帧。**
两件事合起来才成立：

1. `PlayerView` 的 shutter（未出画时的遮罩）默认纯黑，设成透明之后会透出下层早就画好的
   首帧缩略图，出画后自然盖住。所以不需要监听「首帧渲染完成」做淡入；
2. **换片时不清空那张位图**。视频出画要等解码器起播，是几百毫秒级的事；早先在这一刻把
   位图置空，于是从图片切到视频时看到的先是黑屏、再是画面 —— 这就是「切到视频首帧黑一下」
   的成因。现在保留上一件，等新位图解出来再替换，观感就是从一张切到另一张。
   唯一例外是新位图**解不出来**，那时必须清空（留着上一件才是错的）。

**所有开关落盘。**
投屏态、填满/适应、静音、轮播间隔、预览开关与侧别、后台保持、开机自启都存在 `CastPrefs` 里。
逻辑很直白：这个工具的核心诉求是「挂上去就不用管了」，
上次是展出状态，开机就该自己回到展出状态，而不是每次重来一遍。
（`playing` 刻意不落盘 —— 展窗就该自己播起来。）

**解码一律降采样。**
相机原图 4000×3000 直出是 48MB 的 ARGB_8888。`MediaDecoder` 按目标尺寸解码：
网格用 384px、舞台用 2048px，配 `LruCache`（按总内存 1/8 计价）。
`ImageDecoder` 会自动应用 EXIF 旋转，不用自己读 orientation。

## 静态自检（没有 JDK / SDK 也能跑）

```bash
python3 tools/check_cast.py        # 括号配对 / import 完整性 / 符号已声明
python3 tools/check_media_api.py   # 核对用到的 media3 API 要不要 opt-in
```

两个脚本都做过**反向验证**（故意抽掉一行，确认它真的会报）。

`check_media_api.py` 值得单独说，因为这里的机制和直觉不一样：media3 的 `UnstableApi`
元注解是 **`androidx.annotation.RequiresOptIn`**，**不是 `kotlin.RequiresOptIn`**（看注解类
自身的元注解即可确认）。于是：

- **Kotlin 编译器不管它** —— 不写 opt-in，`assembleDebug` 照样成功（0.1.0 版就是这样编过的）。
  真正拦它的是 **lint 的 `UnsafeOptInUsageError`**（release 的 `lintVital` 也会报）。
  这是**静态检查层**约束，不是编译层，但「能编过」不等于没问题；
- 反过来，**把 `@UnstableApi` 标在自己的函数上是错的**：那是把看门狗标记贴到自己身上，
  等于声明「我这个函数也不稳定」，调用方会被一起要求 opt-in。
  局部接受只能用 `@androidx.annotation.OptIn(...)`。

脚本按 `javap -v` 的**成员块**判定（注解打印在成员块**末尾**，早先按「`Code:` 之前」扫是
假阴性：抽象方法能查出、带实现的方法全漏）。当前结论：用到的 25 个 media3 API 里
**3 个带标记**——`PlayerView.setResizeMode` / `setShutterBackgroundColor` /
`setKeepContentOnPlayerReset`，已在 `ui/VideoStage.kt` 一个函数上局部接受；
其余（含 `PlayerView.setPlayer`、`Player.Listener.onPlaybackStateChanged` /
`onPlayerError(PlaybackException)`）都是稳定的。

## 已知限制

- 视频默认静音（`volume = 0f`），开关在设置里；没有做音量条。
- 队列只存 uri，不复制文件。原图被删除或权限失效后该条会被跳过。
- 没做拖拽排序；轮播只支持固定几档间隔，不能自定义秒数。
- **动图不做降采样也不进缓存**（见上文「动图」一节）：AnimatedImageDrawable 不能被两个
  View 共用，尺寸也由原图决定。GIF 体积本来就小，实际影响可忽略；但一张超大的动图
  （几十 MB、几千像素）会明显吃内存。
- **「应用在后台外屏还在显示」取决于厂商实现**：能修的是我们自己这边的（容器 detach、
  判定翻脸、自愈窗口太短），已在 0.4.0 修掉；如果系统主动收起展示容器，
  应用侧只能等回前台补回来，日志里会留下 `容器可见性 -> false`。
- **外屏常亮仍需真机确认一次**：屏幕锁管的是「设备屏幕不按超时熄灭」，理论上覆盖屏与
  内屏同属一个电源组，应该跟着一起常亮；但折叠屏的屏电状态由厂商的 display group 策略
  决定，不排除它对覆盖屏另有安排。验证方式：展出后切到桌面、别碰手机，等过系统屏幕超时
  （设置 → 显示 → 屏幕超时），看外屏是否还亮着。日志入口：
  `adb logcat -s CastService ScreenWake`，应能看到 `外屏常亮 → true（展出=true 后台保持=true 常亮=true）`
  和 `已持有屏幕锁`。
- 分栏预览的**侧别**默认左，需要人对着实物确认一次（厂商堆叠方向决定外屏在左半还是右半）。
- 预览栏里的画面按外屏**长宽比**缩放，但 Compose 布局在真外屏上的实际观感（尤其旋转方向）
  仍需真机核对一次。
- 「开机自启」依赖用户手动授予悬浮窗权限，这是 Android 的限制，绕不过去。
- 保活线程续在低内存压力极大时仍可能被杀；被杀了要等下次开机或手动打开。
- 折起态下外屏是 Activity 本体，此时**没有**窗口区域会话，所以
  「后台保持」在折起态提供的只是进程存活，不是会话存活。
